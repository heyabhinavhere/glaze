## Exact technical reason

An SVG filter applied to an owned HTML/SVG subtree receives that subtree's `SourceGraphic`; it does not receive the already-composited pixels behind the element. With only that legal input, the SVG result must either:

1. render the owned source as a shaped, substantially opaque surface, producing the rejected slab/continuous-contrast boundary; or
2. use continuous thickness as output alpha, which makes the body disappear into the rejected blurred halo rather than transmitting the backdrop.

The honest ways to obtain WebGL-like transmission of pixels behind the material are outside this gate: duplicate the substrate inside the filtered boundary, capture/rasterize arbitrary DOM, use backdrop/CSS material treatment, or depend on non-portable background-image filter inputs. All are prohibited. The remaining endpoint compression is produced by `feDisplacementMap` at the mathematically equivalent shared refraction scale. Reducing only SVG displacement would create a renderer-specific material value; reducing the shared scale would materially retune the locked accepted WebGL reference.

Therefore the failure is architectural, not a missing cosmetic constant.
